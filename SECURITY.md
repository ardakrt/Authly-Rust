# Security

To report a potential vulnerability, use [GitHub private vulnerability reporting](https://github.com/ardakrt/Authly-Rust/security/advisories/new) when available. Otherwise, open an issue requesting a private contact without including account secrets, OTP codes, PINs, passwords or backup contents.

## Boundaries

- The Tauri v2 Rust backend (`src-tauri/`) owns SQLite database access, OS-backed secret encryption (`KeyringAesGcmVault` storing the 32-byte master key in the OS keyring and encrypting each secret with AES-256-GCM), and TOTP generation. The React UI inside the WebView receives safe metadata and display codes through typed, Zod-validated Tauri commands (`src/renderer/src/bridge/tauriBridge.ts`) constrained by Tauri capabilities (`src-tauri/capabilities/default.json`) and Content Security Policy (`src-tauri/tauri.conf.json`); stored secrets are never returned by account-list or import responses.
- Account writes validate Base32 keys and character counts (`AccountService` and `TotpService`). QR migration parsing bounds input (128 KiB, up to 100 accounts) and rejects malformed or unsupported data. Selected QR accounts are encrypted before one atomic SQLite transaction (`create_many`), with PIN lock session-epoch checks before and after encryption.
- Corrupt or unreadable accounts remain isolated in the vault so healthy accounts continue generating codes; unavailable codes cannot be copied from the interface. On Windows, automatic one-time migration from legacy Electron (`%APPDATA%\authapp`) unprotects the DPAPI master key, re-encrypts healthy `v10` secrets with `KeyringAesGcmVault`, and preserves corrupted legacy blobs without aborting migration of healthy accounts.
- The application PIN (PBKDF2-SHA256, 600,000 iterations, constant-time comparison, exponential retry backoff) gates application access, sensitive operations, and settings updates; it is not an independent encryption key for the vault. An unlocked OS session or compromised operating system is outside this protection boundary.
- The Rust backend enforces the inactivity timeout (five minutes by default) via a 1-second background thread, checks OS idle time on Windows (`GetLastInputInfo`), and tracks renderer activity (`record_activity`). Renderer activity cannot unlock a locked session. Locking invalidates the captured session epoch so pending code delivery, clipboard writes, account writes, settings updates, backup operations, and update launches cannot continue under a later unlock.
- The renderer subscribes to Tauri lock-state events (`lock:status-changed`), unmounts account and form state while locked, and allows PIN creation, change, removal, and immediate locking in Settings. It reloads accounts on unlock and fails closed if the initial lock status cannot be checked.
- Encrypted backups (`authapp-backup-v1`) use a version 2 payload containing groups and accounts, deriving a 256-bit key with PBKDF2-SHA256 (600,000 iterations) and encrypting with AES-256-GCM. Restore is transactional across both tables. Version 1 backups remain readable; accounts whose old backups lack group metadata are restored ungrouped with an explicit notice. No account is silently skipped on an import failure.
- TOTP is generated offline. Update checks query the GitHub Releases API (`https://api.github.com/repos/ardakrt/Authly-Rust/releases/latest`) in packaged builds, and update launches (`install_update`) open only verified `https://github.com/ardakrt/Authly-Rust/releases` URLs in the user's external default browser. All UI fonts (`@fontsource/*`) are bundled locally with no external stylesheet or font network requests. See the README for platform-specific storage and backup details.

Never attach a real vault, unencrypted backup, raw QR content, secret key or generated code to an issue or log. Automated tests (`npm run test:web`, `npm run test:rust`) and `npm run smoke` use synthetic fixtures and isolated in-memory storage.
